# SmileSim — دليل المبرمج والمسؤول التقني

آخر تحقق: 2026-11-12، على الكود عند `3a2a3c1` وما فوقه محلياً (سكربتات النسخ الاحتياطي).

هذا الدليل يطابق الكود الفعلي. كل بند يحمل إحدى هذه العلامات:

| العلامة | المعنى |
|---|---|
| ✅ مُجهَّز ومختبَر | موجود في المستودع وجُرِّب (يُذكر على ماذا) |
| ⏳ لم يُفعَّل بعد | مكتوب وجاهز، لم يُشغَّل على الإنتاج |
| ✋ يدوي | لا يقوم به النظام؛ يفعله المسؤول التقني بيده |
| 🔐 يحتاج موافقة المالك | لا يُنفَّذ إلا بقرار صريح من مالك المشروع |

**حالة النسخ الاحتياطي (قرار المالك، 2026-11-12): جاهز برمجياً وغير مفعَّل تشغيلياً.** السكربتات مكتملة ومختبَرة على بيانات اصطناعية وعلى مخزن S3 وهمي محلي، **ولم تُختبر على Cloudflare R2 الحقيقي**. لا تعمل تلقائياً بنشر الـAPI أو الـWorker: ليست داخل أي صورة، وتفعيلها لكل عميل يتطلب تركيبها على الخادم وملف إعدادات وخطوة تشغيل صريحة (البند 9). كل قيم العميل (الحساب، الـBucket، المفاتيح) من ملف الإعدادات، ولا قيمة ثابتة في الكود.

**لا يوجد في هذا الدليل أي سرّ حقيقي.** كل قيمة بين `< >` تملؤها أنت، ولا تُكتب في Git ولا في أي وثيقة تُشارَك.

## 1. البنية المعمارية

SmileSim مكتب جملة لشرائح الاتصال بأربع طبقات («أبواب») تُحدَّد من اسم النطاق:

| الباب | النطاق الفرعي | الطبقة |
|---|---|---|
| الفرع (الإدارة) | `admin.` | `branch` |
| الوكيل الرئيسي | `main.` | `main_agent` |
| الوكيل | `agent.` | `agent` |
| نقطة البيع | `pos.` | `pos` |

المستودع واحد (npm workspaces):

- `apps/web` — واجهة Next.js. المتصفح يكلّم الواجهة فقط؛ كل طلب إلى `/api/...` تعيد الواجهة توجيهه داخلياً إلى الـAPI.
- `apps/api` — خدمة NestJS مع Prisma. منها تُبنى صورة واحدة تعمل بدورين: **API** و**Worker**.
- قاعدة البيانات PostgreSQL 16، وRedis 7.

```
المتصفح ──HTTPS──> Traefik (وكيل Coolify) ──> web :3000 ──/api──> api :3001 ──> PostgreSQL
                                                                      │  └────> Redis
                                                             worker ──┘ (الصورة نفسها، APP_ROLE=worker)
```

مراجع البنية التفصيلية: `docs/architecture/backend.md` و`docs/architecture/frontend.md` والقرارات في `docs/architecture/decisions/`.

## 2. الخدمات

| الخدمة | ما تفعله | المنفذ | ملاحظات |
|---|---|---|---|
| **Web** | الواجهة، وإعادة توجيه `/api` إلى الـAPI | 3000 | الوحيدة التي لها نطاق عام |
| **API** | كل منطق النظام؛ تطبّق migrations عند كل إقلاع ثم تبدأ | 3001 | بلا نطاق عام ولا منفذ منشور؛ يوصَل إليها عبر الواجهة |
| **Worker** | مهام الخلفية (تنظيف سجل النشاط؛ إرسال عمليات المزوّد **متوقف في الإنتاج**) | — | الصورة نفسها بـ`APP_ROLE=worker`؛ لا يطبّق migrations |
| **PostgreSQL 16** | كل بيانات العمل | 5432 داخلي | volume واحد على الخادم |
| **Redis 7** | مفاتيح الجلسات الحيّة، عدّادات الحدّ من الطلبات، قائمة المهام | 6379 داخلي | فقدانه يسجّل خروج المستخدمين فقط |

فحص الصحة: الـAPI يجيب `GET /health` بـ`{"ok":true}`. الواجهة تجيب `/login`. الـWorker بلا منفذ؛ صحته أن عمليته تعمل.

## 3. تجهيز خادم جديد من الصفر — ✋ يدوي

1. خادم Linux (Ubuntu حديث)، 2 vCPU و4 غيغابايت ذاكرة على الأقل، 40 غيغابايت قرص. البناء يحتاج نحو 10 دقائق للخدمات الثلاث.
2. مستخدم بصلاحية `sudo`، ودخول SSH بمفتاح لا بكلمة سر.
3. جدار ناري: المنافذ 22 و80 و443 فقط للعالم. لا تفتح 3000 ولا 3001 ولا 5432 ولا 6379.
4. تثبيت Coolify بسكربته الرسمي من موقع Coolify (راجع توثيقهم للأمر الحالي)، ثم إنشاء حساب المدير وتفعيل التحقق بخطوتين له.

## 4. ربط Coolify وGitHub — ✋ يدوي

الإعداد الفعلي الحالي: **ثلاثة تطبيقات من نوع Dockerfile** من المستودع نفسه وفرع `main`، وموردا قاعدة بيانات:

| التطبيق في Coolify | Dockerfile | أمر التشغيل | المنفذ |
|---|---|---|---|
| smilesim-web | `/apps/web/Dockerfile` | الافتراضي | 3000 |
| smilesim-api | `/apps/api/Dockerfile` | الافتراضي (migrations ثم الـAPI) | 3001 |
| smilesim-worker | `/apps/api/Dockerfile` | `node dist/worker.js` مع `APP_ROLE=worker` | — |
| smilesim-postgres | PostgreSQL 16 (مورد قاعدة بيانات) | — | — |
| smilesim-redis | Redis 7 | — | — |

- سياق البناء هو **جذر المستودع** للتطبيقات الثلاثة.
- المستودع عام، فالربط بلا GitHub App. **الدفع إلى `main` لا ينشر تلقائياً**: لا يوجد webhook في GitHub. النشر يُطلَب يدوياً من Coolify. (مفتاح «Auto Deploy» في Coolify مفعَّل لكنه بلا أثر دون webhook؛ يُفضَّل إطفاؤه للوضوح. 🔐)
- `README.md` يصف بديلاً بمورد Docker Compose واحد يقرأ `docker-compose.yml`. كلاهما يعمل؛ المنشور فعلاً هو الثلاثة تطبيقات.
- GitHub Actions (`.github/workflows/ci.yml`) يختبر ويبني فقط ولا ينشر: lint، typecheck، اختبارات الـAPI، اختبارات PostgreSQL وRedis، البناء، واختبارات الواجهة.

## 5. النطاقات وDNS وHTTPS — ✋ يدوي

- خمسة أسماء كلها تشير إلى الخادم (سجل A) وتُربط بتطبيق **الواجهة** في Coolify: النطاق الأساسي و`admin.` و`main.` و`agent.` و`pos.`.
- الـAPI **لا** يُعطى نطاقاً.
- HTTPS تصدره Coolify تلقائياً (Let's Encrypt عبر Traefik) لكل نطاق مربوط.
- إن استُخدم Cloudflare للـDNS: اليوم هو للأسماء فقط (بلا وكيل). تفعيل وكيل Cloudflare يضيف قفزة أمام الخادم ويغيّر قيمة `TRUST_PROXY` (البند 6).

## 6. متغيرات البيئة

المصدر الوحيد لأسماء متغيرات الـAPI هو `apps/api/src/config.ts`. الـAPI **يرفض الإقلاع** في الإنتاج إن كان أيٌّ من المعلَّمة بـ«إلزامي» غير صحيح (`apps/api/src/production-config.ts`)، ويكتب اسم المتغير والقاعدة، لا القيمة.

### تطبيق الـAPI (وقت التشغيل)

| المتغير | الوظيفة | القيمة في الإنتاج |
|---|---|---|
| `DATABASE_URL` | عنوان PostgreSQL | **إلزامي**. سرّ |
| `REDIS_URL` | عنوان Redis | **إلزامي**، يبدأ بـ`redis://` أو `rediss://`. سرّ |
| `SECRETS_KEY` | مفتاح تشفير رموز eSIM وأسرار المصادقة الثنائية | **إلزامي**: 32 بايت بترميز base64. سرّ |
| `COOKIE_SECURE` | الكوكي لا يُرسل إلا عبر HTTPS | **إلزامي**: `true` |
| `WEB_ORIGIN` | عناوين الواجهة المسموحة، بفواصل | **إلزامي**: أصول `https` بلا مسار |
| `TRUST_PROXY` | عدد الوكلاء العكسيين الموثوقين أمام الـAPI | **إلزامي**: عدد صحيح. انظر أدناه |
| `COOKIE_DOMAIN` | النطاق الأب المشترك بين الأبواب، لتعمل جلسة واحدة | النطاق الأساسي |
| `WEBAUTHN_RP_ID` | هوية مفاتيح المرور (Passkeys) | اختياري؛ الافتراضي النطاق بلا أول جزء |
| `PROVIDER_SIMULATION` | محاكاة المزوّد | **يجب** أن يكون غير مضبوط أو `0` |
| `PROVIDER_DISPATCH` | مُرسِل عمليات المزوّد (مع `PROVIDER_ADAPTERS` و`PROVIDER_TARGET` و`DEPLOYMENT_ID`، انظر قسم الـWorker) | **غير مضبوط**. كان: لا أثر له في الإنتاج (متوقف دائماً) |
| `TRIAL_SEED`, `TRIAL_SEED_ALLOW_PRODUCTION` | حسابات التجربة بكلمة سر منشورة | **يجب** ألا يكونا `true` |
| `PORT` | منفذ الاستماع | الافتراضي 3001 |
| `NODE_ENV` | — | الصورة تضبطه `production` |

**`TRUST_PROXY`:** في البنية الحالية القيمة بالتحليل **`1`** (Traefik يتجاهل الرؤوس التي يرسلها العميل ويكتب العنوان الحقيقي؛ والواجهة تمرّر الرأس دون إضافة). تُؤكَّد بعد كل تغيير في البنية بطلبَي دخول من عنوان معروف: عادي، وآخر برأس `X-Forwarded-For` مزوّر؛ سجل النشاط يجب أن يُظهر العنوان الحقيقي في الحالتين. ⏳ لم تُضبط على الخادم الحالي بعد.

### تطبيق الـWorker

`DATABASE_URL`، `REDIS_URL`، `APP_ROLE=worker`. لا يحتاج `SECRETS_KEY` ما دام إرسال عمليات المزوّد متوقفاً.

منذ الشريحة S.12a يفحص الـWorker إعداداته عند الإقلاع قبل أن يفتح Redis أو قاعدة البيانات، ويرفض الإقلاع في الإنتاج إذا كانت ناقصة أو متضاربة (الرسالة تسمّي المتغيّر والقاعدة، لا القيمة). ويشغّل دائماً جزء **التسوية** من عمليات المزوّد (نقل الرسائل، تطبيق النتائج، الاسترداد)، وهو قراءة فقط ما دام لا توجد عمليات. أما **الإرسال** إلى مزوّد فمتوقف، ولا يشتغل إلا بالمتغيّرات الثلاثة أدناه معاً، وبموافقة مالك الفرع على المزوّد، وبوجود Adapter للمزوّد داخل الصورة. **الصورة الحالية لا تحتوي أي Adapter، فلا يُرسَل شيء مهما ضُبط.**

| المتغير | الوظيفة | القيمة اليوم |
|---|---|---|
| `PROVIDER_DISPATCH` | يسمح بإرسال عمليات المزوّد عند `1` | **غير مضبوط** |
| `PROVIDER_ADAPTERS` | أكواد المزوّدين المسموح ببناء Adapter لهم، مفصولة بفواصل | **غير مضبوط** |
| `PROVIDER_TARGET` | هدف النشر: `sandbox` أو `live` | **غير مضبوط** |
| `DEPLOYMENT_ID` | اسم هذا النشر (3 إلى 63 حرفاً صغيراً أو رقماً أو `-`، مثل `staging-1`). موافقة المالك وإشهاد الـWorker يُكتبان بهذا الاسم ولا يسريان على نشر آخر، حتى لو شاركه قاعدة البيانات أو استُعيدت قاعدته من نسخته الاحتياطية. إلزامي عند `PROVIDER_DISPATCH=1` | **غير مضبوط** |
| `SECRETS_KEY` | مطلوب على الـWorker عند `PROVIDER_DISPATCH=1` (يفتح بيانات اعتماد المزوّدين) | غير مطلوب الآن |

الأربعة الأولى تُضبط **بالقيم نفسها على الـAPI والـWorker**، ولكل نشر اسم خاص به لا يُعاد استعماله في نشر آخر. إن اختلفت بينهما لا يُرسَل شيء وتذهب كل عملية بيع إلى المسار اليدوي. ضبط بعضها دون الباقي خطأ يمنع الإقلاع في الإنتاج. **لا تضبط أياً منها قبل تسليم أول Adapter (الشريحة S.12b) واجتياز قائمة الانطلاق.**

**عند تغيير بيانات اعتماد مزوّد** (من شاشة المالك): تُسحب موافقة المالك على المزوّد فوراً ويتوقف الإرسال الجديد له، ويعيد الـWorker بناء اتصاله بالبيانات الجديدة خلال 20 ثانية تقريباً دون إعادة تشغيل. لا يُستأنف الإرسال إلا بعد أن يوافق المالك من جديد. ما أُرسل قبل التغيير يكتمل ويُسوّى كالمعتاد، ولا يُفك أي حجز.

**عند توقف الـWorker**: تذهب عمليات البيع الجديدة إلى المسار اليدوي. إذا توقف فجأة (دون إيقاف منظّم) قد تُفتح عمليات على مسار المزوّد لمدة دقيقة واحدة على الأكثر؛ هذه تبقى منتظرة بحجزها ولا تُرسَل حتى يعود Worker، ويستطيع مُرسِلها إلغاءها.

### تطبيق الواجهة

| المتغير | الوظيفة | متى |
|---|---|---|
| `API_PROXY_URL` | العنوان **الداخلي** للـAPI الذي تُعاد إليه طلبات `/api` | وقت البناء والتشغيل |
| `NEXT_PUBLIC_API_URL` | يُدمج في الحزمة وقت البناء | **وقت البناء**: تغييره يستلزم إعادة بناء الواجهة |

### أين تُضبط

في صفحة «Environment Variables» لكل تطبيق في Coolify. لا في المستودع، ولا في `docker-compose.yml`، ولا في ملف `.env` مرفوع.

## 7. المفاتيح والأسرار

| السرّ | الغرض | أين يعيش | أين **لا** يعيش |
|---|---|---|---|
| `SECRETS_KEY` | تشفير رموز eSIM وأسرار TOTP داخل القاعدة | متغيرات تطبيق الـAPI + نسختان خارج الخادم | Git، الواجهة، الـWorker |
| المفتاح **العام** للنسخ الاحتياطي | تشفير النسخ على الخادم | الخادم: `/etc/smilesim-backup/backup-public.asc` | — (ليس سرّاً) |
| المفتاح **الخاص** للنسخ الاحتياطي + عبارة مروره | فك النسخ عند الاسترجاع | مدير كلمات السر للمالك + نسخة غير متصلة | **خادم الإنتاج، إطلاقاً** |
| اعتماد R2 للكتابة («Object Read & Write») | رفع النسخ | الخادم: `/etc/smilesim-backup/backup.env` (600، للجذر) | Git |
| اعتماد R2 للقراءة فقط («Object Read only») | جلب نسخة للاسترجاع | مع المفتاح الخاص، خارج الخادم | خادم الإنتاج |
| `DATABASE_URL`، `REDIS_URL` | الاتصال بالبيانات | Coolify | Git |
| حساب Cloudflare، حساب GitHub، مدير Coolify، مفتاح SSH | إدارة البنية | مدير كلمات السر، مع تحقق بخطوتين | — |

لا توجد اليوم أسرار لمزوّدي الخدمة ولا لبوابات SMS أو البريد: الربط بالمزوّدين وبوابات الإرسال غير مفعَّلين في هذا الكود.

سجل الأسرار (بلا قيم) في `secrets-register-template-ar.md`.

## 8. توليد المفاتيح ونقلها بأمان — ✋ يدوي، 🔐

كل توليد يتم **على جهاز المالك**، لا على الخادم، ولا تُلصق القيم في محادثة أو بريد أو تذكرة.

**`SECRETS_KEY`:**
```bash
openssl rand -base64 32
```
تُلصق مرة واحدة في متغيرات تطبيق الـAPI في Coolify (وقت التشغيل فقط). التحقق منه دون عرضه، داخل حاوية الـAPI، يطبع الطول ويجب أن يكون `32`:
```bash
node -e "console.log(Buffer.from(process.env.SECRETS_KEY||'','base64').length)"
```

**زوج مفاتيح النسخ الاحتياطي (OpenPGP)، بعبارة مرور:**
```bash
gpg --quick-gen-key "SmileSim backup <اسم العميل>" ed25519 cert never
gpg --quick-add-key <بصمة المفتاح> cv25519 encr never
gpg --armor --export <البصمة> > backup-public.asc          # هذا فقط يذهب إلى الخادم
gpg --armor --export-secret-keys <البصمة> > backup-private.asc   # يبقى خارج الخادم
```

**النقل:** المفتاح العام يُنسخ إلى الخادم عبر `scp`. المفتاح الخاص وعبارة مروره و`SECRETS_KEY` يُحفظ كلٌّ منها في مكانين خارج الخادم (مدير كلمات سر + نسخة غير متصلة). **فقدان المفتاح الخاص يجعل كل النسخ بلا قيمة؛ فقدان `SECRETS_KEY` يجعل رموز eSIM وأسرار TOTP غير مقروءة حتى بعد استرجاع القاعدة.**

## 9. ربط Cloudflare R2 وتفعيل النسخ التلقائي

الحالة: السكربتات ✅ مُجهَّزة ومختبَرة على بيانات اصطناعية ومخزن S3 محلي وهمي. ⏳ **لم يُنشأ Bucket، ولم يُختبر الرفع على R2 الحقيقي، ولم تُفعَّل الجدولة.** كل ما يلي 🔐.

### 9.1 إعداد Cloudflare — ✋ يدوي (في لوحة Cloudflare)

1. **Bucket خاص:** R2 ← Create bucket، باسم مثل `smilesim-backups-<العميل>`. الـBucket خاص افتراضياً؛ **لا** تفعّل «Public Development URL» ولا نطاقاً مخصصاً.
2. **قاعدتا قفل** (Settings ← Bucket lock rules): تمنعان الحذف والاستبدال:
   - البادئة `smilesim/daily/` لمدة 90 يوماً.
   - البادئة `smilesim/monthly/` لمدة 365 يوماً.
3. **قاعدتا دورة حياة** (Settings ← Object lifecycle rules): الحذف بعد انتهاء القفل:
   - `smilesim/daily/` بعد 91 يوماً.
   - `smilesim/monthly/` بعد 366 يوماً.
4. **رمزان (R2 ← Manage API tokens)، كلاهما «Account API token» ومحصور بهذا الـBucket وحده:**
   - «Object Read & Write» للخادم.
   - «Object Read only» للاسترجاع، يُحفظ خارج الخادم.
   لكل رمز Access Key ID وSecret Access Key يُعرضان **مرة واحدة**.
5. حساب Cloudflare نفسه بتحقق بخطوتين: من يملكه يستطيع إزالة قواعد القفل.

ملاحظات من توثيق Cloudflare (قُرئت 2026-11-12): R2 لا يدعم إصدارات الكائنات ولا واجهة S3 Object Lock؛ الحماية هي «Bucket locks». لا يوجد رمز للكتابة فقط: رمز الخادم يستطيع القراءة أيضاً، لكن ما يقرؤه نص مشفَّر لا يُفتح بلا المفتاح الخاص.

### 9.2 على الخادم — ✋ يدوي، 🔐

```bash
sudo mkdir -p /opt/smilesim-backup /etc/smilesim-backup /var/backups/smilesim
sudo cp -R scripts/backup/* /opt/smilesim-backup/            # من نسخة المستودع
sudo cp backup-public.asc /etc/smilesim-backup/
sudo cp scripts/backup/backup.env.example /etc/smilesim-backup/backup.env
sudo chmod 600 /etc/smilesim-backup/backup.env && sudo chmod 700 /var/backups/smilesim
```
ثم املأ `/etc/smilesim-backup/backup.env`: إعدادات `backup.env.example` وإعدادات `r2.env.example` معاً في الملف نفسه، مع:
```
BACKUP_UPLOAD_CMD=/opt/smilesim-backup/r2-upload.sh
BACKUP_ALERT_CMD=<أمر التنبيه>           # يُستدعى: <الأمر> "<العنوان>" "<سطر واحد>"
BACKUP_HEARTBEAT_URL=<اختياري: عنوان نبضة لمراقب خارجي>
BACKUP_MAX_AGE_HOURS=26
```
`BACKUP_PG_CONTAINER` هو اسم حاوية PostgreSQL كما يظهر في `docker ps`.

### 9.3 أول نسخة ثم الجدولة — 🔐

```bash
sudo /opt/smilesim-backup/run-scheduled.sh /etc/smilesim-backup/backup.env    # نسخة واحدة باليد
sudo cp /opt/smilesim-backup/systemd/smilesim-backup*.{service,timer} /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now smilesim-backup.timer smilesim-backup-check.timer   # هذه هي خطوة التفعيل
```
- الوقت الافتراضي 02:30 بتوقيت الخادم. لتغييره: `sudo systemctl edit smilesim-backup.timer` وضبط `OnCalendar=`.
- لا تعمل نسختان معاً: السكربت يقفل ويرفض الثانية.
- مؤقّت ثانٍ يفحص كل 6 ساعات: إن لم تنجح نسخة خلال `BACKUP_MAX_AGE_HOURS` يُرسَل تنبيه.

## 10. التأكد من نجاح النسخ

```bash
sudo tail -5 /var/backups/smilesim/backup.log        # سطر لكل تشغيل: OK <المعرّف> <الحجم>  أو  FAILED <السبب>
systemctl list-timers 'smilesim-backup*'             # موعد التشغيل القادم والسابق
sudo /opt/smilesim-backup/check-freshness.sh /etc/smilesim-backup/backup.env
```
ومن جهاز الاسترجاع (باعتماد القراءة فقط): `scripts/backup/r2-fetch.sh list` يسرد النسخ المحفوظة في R2.

**نسخة موجودة ليست نسخة صالحة حتى تُسترجَع.** التمرين الدوري (أسبوعياً، من جهاز غير الخادم يملك المفتاح الخاص):
```bash
scripts/backup/verify-latest.sh <ملف إعدادات فيه R2 للقراءة و BACKUP_PRIVATE_KEY>
```
يجلب أحدث نسخة، يسترجعها في PostgreSQL 16 مؤقت بلا شبكة، يقارن كل جدول وقيد وفهرس بما سُجّل، ويكتب `VERIFIED` في سجل التمارين.

## 11. استرجاع النظام كاملاً بعد تعطل الخادم

ما تحتاجه: المستودع، المفتاح الخاص وعبارة مروره، اعتماد R2 للقراءة، `SECRETS_KEY`، وإعدادات البيئة (البند 6).

1. خادم جديد وCoolify (البندان 3 و4)، وموردا PostgreSQL 16 وRedis 7 فارغان.
2. على جهازك (لا على الخادم): جلب أحدث نسخة والتحقق منها.
   ```bash
   scripts/backup/r2-fetch.sh latest ./restore
   scripts/backup/verify-restore.sh ./restore/<المعرّف>.dump.gpg ./restore/<المعرّف>.manifest
   ```
   لا تكمل بلا سطر `VERIFIED`.
3. الاسترجاع إلى قاعدة الإنتاج الجديدة — ✋ يدوي، 🔐. **لا يوجد سكربت آلي لهذه الخطوة عمداً.** فك التشفير يتم على جهازك ويُمرَّر عبر SSH مباشرة إلى `pg_restore` داخل حاوية PostgreSQL الجديدة، دون ملف واضح على أي قرص:
   ```bash
   gpg --decrypt ./restore/<المعرّف>.dump.gpg \
     | ssh <الخادم الجديد> 'sudo docker exec -i <حاوية postgres> sh -c "pg_restore --no-owner --no-privileges --exit-on-error -U \"\$POSTGRES_USER\" -d \"\$POSTGRES_DB\""'
   ```
4. ضبط متغيرات البيئة للتطبيقات الثلاثة، وبالأخص **`SECRETS_KEY` نفسه** الذي كان على الخادم القديم.
5. نشر الـAPI (يطبّق أي migrations ناقصة)، ثم الـWorker، ثم الواجهة. النطاقات وDNS (البند 5).
6. المستخدمون يسجّلون الدخول من جديد (Redis فارغ).
7. إعادة تركيب النسخ الاحتياطي على الخادم الجديد (البند 9).

**ما يُفقَد:** كل ما كُتب بعد آخر نسخة ناجحة (حتى 24 ساعة مع نسخة ليلية).

**قاعدة فارغة بلا نسخة:** لا يوجد في الكود ما ينشئ أول صاحب فرع في الإنتاج (حسابات التجربة ممنوعة هناك). الـAPI يقلع ويحذّر في السجل أن لا حسابات. إنشاء أول حساب عندها ✋ يدوي بإدخال صف في القاعدة، وهو فجوة معروفة.

## 12. تغيير الخادم أو النطاق — 🔐

**الخادم:** نافذة صيانة ← إيقاف الـAPI والـWorker ← `backup.sh --final` ← التحقق منها ← البند 11 على الخادم الجديد ← تحويل DNS ← إبقاء القديم متوقفاً أياماً ثم مسحه.

**النطاق:** تتغير معه: نطاقات تطبيق الواجهة في Coolify، `WEB_ORIGIN`، `COOKIE_DOMAIN`، و`WEBAUTHN_RP_ID` إن كان مضبوطاً. مفاتيح المرور (Passkeys) مربوطة بالنطاق: تغييره يبطلها ويسجّل أصحابها من جديد.

## 13. التحديث والتراجع — 🔐

الخطة التفصيلية للترقية الحالية: `docs/operations/2026-11-12-coolify-upgrade-preparation.md`. القواعد العامة:

- CI أخضر على الـcommit المراد نشره، مع قراءة نتيجة اختبارات الواجهة (مهمتها غير مانعة).
- **الـmigrations تُطبَّق عند إقلاع الـAPI.** بعد تطبيقها، إعادة نشر الصورة القديمة ليست تراجعاً مضموناً. التراجع المضمون هو استرجاع نسخة أُخذت قبل النشر مباشرة.
- لذلك قبل أي نشر يحمل migrations: نافذة صيانة، إيقاف الكتابة، `backup.sh --final`، `verify-restore.sh`، ثم النشر.
- الترتيب: الـAPI ثم الـWorker ثم الواجهة. إن تغيّر عقد الاستجابات بين الإصدارين فالثلاثة تتغير معاً داخل النافذة.
- النشر يُطلَب يدوياً من Coolify لكل تطبيق. التراجع من Coolify إلى صورة سابقة محفوظة، بعد استرجاع القاعدة إن لزم.
- تجربة الترقية مسبقاً على نسخة مستعادة: `verify-restore.sh ... --keep` ثم `rehearse-upgrade.sh`.

**ترحيل رموز eSIM القديمة (Backfill):** يدوي ولا يعمل عند الإقلاع. داخل حاوية الـAPI:
```bash
node dist/seal-secrets.js --dry-run     # يعدّ فقط
node dist/seal-secrets.js               # يشفّر؛ آمن للإيقاف وإعادة التشغيل
```
⏳ لم يُشغَّل على أي بيئة. 🔐

**تقارير قراءة فقط** داخل حاوية الـAPI: `node dist/reservation-conflicts.js` (تعارض حجوزات الشرائح قبل النشر)، و`node dist/two-factor-methods.js` (إعدادات تحقق بخطوتين تذكر SMS أو البريد).

## 14. المراقبة وحل الأعطال

**الحالة الحالية على الخادم:** فحوص الصحة في Coolify **معطّلة** للتطبيقات الثلاثة. ⏳ الصور لا تحتوي `curl` ولا `wget`، ففحص Coolify المبني على مسار ومنفذ سيفشل؛ الفحص يجب أن يكون أمراً بـ`node`:
```bash
node -e "fetch('http://127.0.0.1:3001/health').then(r=>process.exit(r.ok?0:1)).catch(()=>process.exit(1))"
```
(وللواجهة العنوان `http://127.0.0.1:3000/login`). مهلة بدء 60 ثانية، كل 10 ثوانٍ، 6 محاولات.

| العَرَض | أول ما يُفحص |
|---|---|
| الـAPI يعيد التشغيل مراراً | سجله: سطر `Config` يسمّي المتغير الخاطئ؛ أو migration فشلت |
| الدخول يفشل للجميع | Redis يعمل؟ `REDIS_URL` صحيح؟ |
| «تعذّر حفظ رمز eSIM بأمان» | `SECRETS_KEY` مفقود أو غير صالح في الـAPI |
| «تعذّرت قراءة رمز eSIM المحفوظ» | المفتاح تغيّر، أو قيمة تالفة؛ تُصلَح بمهمة تغيير شريحة |
| الواجهة تعمل والطلبات تفشل | `API_PROXY_URL` في الواجهة، وهل الـAPI يجيب `/health` |
| تنبيه «backup FAILED» أو «STALE» | `backup.log`، ثم `run-scheduled.sh` باليد |

السجلات: من Coolify لكل تطبيق، أو `sudo docker logs <الحاوية>`. السجلات لا تحمل أسراراً ولا رموز eSIM بتصميم الكود.

## 15. سياسة النسخ الاحتياطي والاسترجاع

- **ماذا:** قاعدة PostgreSQL كاملة. لا يُنسخ Redis. `SECRETS_KEY` ليس في النسخة ويُحفظ منفصلاً.
- **متى:** ليلياً، ونسخة «نهائية» قبل أي ترقية أو تراجع.
- **كيف:** لقطة واحدة متسقة، تُشفَّر بمفتاح عام داخل حاوية القاعدة قبل أن تلمس أي قرص، ثم تُرفع إلى R2 باسم لا يُستبدل.
- **الاحتفاظ:** 7 نسخ محلية؛ في R2 يومية 90 يوماً وأول نسخة كل شهر 365 يوماً، بقفل يمنع الحذف طوال المدة.
- **الإثبات:** تمرين استرجاع أسبوعي من جهاز غير الخادم. لا ترقية بلا `VERIFIED` لنسخة أُخذت قبلها مباشرة.
- **التنبيه:** عند فشل نسخة، وعند مرور 26 ساعة بلا نسخة ناجحة، وعند فشل تمرين.

التفاصيل والاختبارات: `docs/operations/backup-and-restore.md`.

## 16. عند اختراق الخادم أو فقدان مفتاح — 🔐

**اختراق الخادم (أو الشك فيه):**
1. عزل الخادم، وعدم الوثوق بأي شيء عليه.
2. تدوير كل ما كان عليه: اعتماد R2 للكتابة (حذف الرمز وإنشاء جديد)، كلمة سر القاعدة وRedis، `SECRETS_KEY` (انظر أدناه)، مفتاح SSH، ورموز Coolify.
3. النسخ في R2 تبقى سليمة: الخادم لا يملك مفتاح فتحها، والقفل يمنع حذفها.
4. خادم جديد واسترجاع (البند 11) من نسخة سابقة للاختراق.
5. إنهاء كل الجلسات وإلزام المستخدمين بكلمات سر جديدة.

**فقدان `SECRETS_KEY`:** رموز eSIM المشفَّرة وأسرار TOTP غير قابلة للاسترجاع. المالك يعيد تعيين التحقق بخطوتين لكل حساب، ورموز eSIM يُعاد إصدارها من المزوّد عبر مهام تغيير الشريحة. **تدوير المفتاح دون فقدانه غير مدعوم في الكود اليوم** (لا أداة لإعادة التشفير بمفتاح جديد): فجوة معروفة.

**فقدان المفتاح الخاص للنسخ:** النسخ الموجودة لا تُفتح. يُولَّد زوج جديد فوراً ويوضع المفتاح العام على الخادم وتؤخذ نسخة جديدة ويُتحقق منها.

**تسرّب اعتماد R2:** حذف الرمز من Cloudflare وإنشاء بديل. ما قرأه المهاجم نص مشفَّر.

**تسرّب المفتاح الخاص:** زوج جديد، ونسخ جديدة؛ النسخ القديمة تُعامَل كمكشوفة لمن يملكها مع اعتماد قراءة.
