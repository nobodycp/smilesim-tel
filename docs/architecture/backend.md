## Rules

`.cursor/rules/backend-engineering.mdc` is the law for this app; `src/architecture.spec.ts` and `src/architecture-boundaries.spec.ts`
enforce it on every test run (a ratchet: a rule's violation count may only go down). What no refactor may change
about money is `docs/architecture/financial-invariants.md`. Read it before the first change.

## How a request runs

1. Middleware, on every route: `OriginMiddleware` (a write from another site is 403) → `RateLimitMiddleware` →
   `DoorMiddleware`.
2. Global providers (`modules/platform/api-providers.ts`, registered in `AppModule` and in every HTTP spec app):
   `ApiExceptionFilter` (every error is `{ message, code }`) and `EmptyBodyPipe` (a missing body is `{}`).
3. Office controllers: `ActivityInterceptor` then `ActorInterceptor`; the handler gets `@Actor()`.
4. The service: permission through `access/policy.ts` → `parseInput(<Schema>, body)` from `<domain>.schemas.ts` →
   rules (pure: `catalog/rules/`, `pricing/rules/`, `sales/rules/`, and beside their domain) → `<domain>.repository.ts` (one named method per query; a method that may run in
   a transaction takes the client). Money and status changes run in `UnitOfWork.runTx` on locked rows.
5. A line operation asks `ProviderGateway` whether the provider ran it; a refusal or a manual mode opens a task.

## Stack

NestJS 12 · Prisma 7 (`@prisma/adapter-pg`, PostgreSQL) · BullMQ + ioredis · argon2 · otplib (TOTP) · Swagger at `/docs` (non-production only) · Jest 30 + ts-jest 29 + supertest.

## Cross-cutting patterns

- **Permissions:** `ActorInterceptor` resolves the actor before the handler (declared after `ActivityInterceptor`, so
  refused sessions are still logged; pipes run after it, so 401 precedes 400). Services ask `access/policy.ts`
  (`requireGrant(actor, 'edit')`, `holds`, `requireOwner`, `refuseEntered`); none reads `actor.grants` itself.
  `testing/permissions.http.spec.ts` pins who gets past every route. An entered session cannot use `/auth` writes
  and only an account below the branch can be entered.
- **Errors:** `fail(status, code)` throws `ApiFailure`; `ApiExceptionFilter` answers `{ message, code }` for it,
  for framework errors, for a lost unique race (409) and a missing row (404), and a statement cut by its time limit
  (DB.15) as 500 `TOO_SLOW` (not 503: the web takes 502/503/504 for a gateway's answer), kept and logged as `57014`;
  anything else is 500 `SERVER_ERROR`, logged. Status table: 400 invalid or refused by a rule · 401 no session · 403 not allowed · 404 missing or not
  visible · 409 conflict (`*_TAKEN`, `*_EXISTS`, `DUPLICATE_REQUEST`) · 429 rate limit.
- **Validation:** every body is parsed by a zod schema in `<domain>/<domain>.schemas.ts` through `parseInput()`
  right after the permission check (ADR 0002, finished 2026-11-10). Specific error codes keep their own checks.
  Query filters are still read with `text()`.
- **Activity log:** `@Activity(action, subjectKind, subject)` or `@NoActivity(why)` on every office write. The `/auth`
  routes have no interceptor: each handler records through `AuthRecords` (`auth/auth-records.ts`), which writes to `ActivityRecorder`. `ActivityRecorder` is the platform's port
  (`platform/activity.ts`); auditing implements it (slice R.2).
- **Persistence:** `PrismaService` is injected; `runTx` = `$transaction` at Read Committed, notices published after
  commit.
- **Money:** Int agorot. `move()` locks the wallet row before reading it (ADR 0004); two wallets are locked in
  sorted order (`lockWallets`); a line is locked before any wallet. A task holds its price while open and charges
  the price it was opened at: completion **captures** the hold (`WalletLedger.capture`, ADR 0019 D10: the hold
  becomes the charge with no second ceiling check, refused when the wallet holds less than the task's hold);
  `move` and `capture` post through the same code. Two operations are the exception to the fixed price, by
  the owner's rule (rule 1.5): a package switch's difference and a disconnect's refund are the money of the day
  the operation is carried out, worked out in the completion's transaction. A switch's amount is covered by its
  hold up to the hold's size and only an increase beyond it is checked against the ceiling; a disconnect's refund
  is a credit and its task holds nothing (`lines/execution-date-settlement.db.spec.ts`). Proof: `wallets/wallet-concurrency.db.spec.ts`, `lines/line-concurrency.db.spec.ts`
  (PostgreSQL, CI `db` job). `lines/activation-reservation.db.spec.ts` shows the reservations under concurrency.
- **A period carries its own cost, and a disconnect never takes money (package plan D.1).** Every prepaid wallet row
  (`activate`, `charge`, `extend`, `reactivate`, `switch`) stores `periodCost`: the branch's cost for the whole period it
  bought, without the eSIM fee. `openPeriods` hands it on (`OpenPeriod.cost`; the newest switch reprices it like the
  price), and `settleDisconnect` and `LinePricing.switchQuote` use it for the running period; rows written before it
  fall back to the line's terms. `settleDisconnect` answers `refundable: false` when the unused days are worth no
  more than `DISCONNECT_FEE`: the direct disconnect, its quote and the opening of its task refuse with
  `NOTHING_TO_REFUND`; a task that waited until then still closes, with an entry of amount 0 that keeps the
  provider's cost (the number is already disconnected at the provider). Period helpers take days: `daysOf(months)`,
  `periodEnd(from, days)`, `lastWindow(now, endsAt, days, …)`, `switchOver(periods, price, days)`, `periodOf(days, endsAt)`.
- **Lock order (ADR 0019):** task row → line row → the keys of a serial and a number (`lockClaim`: serial, then
  number) → provider operation → wallets in sorted order. A transaction takes only what it needs, in that order.
- **Line state:** a status changes only through `moveLineStatus` (guarded) on a line locked with `lockLine`; a
  request validated before the transaction calls `lockUnchanged` first (409 when another operation got there
  first); a task whose line moved on is refused (`assertTaskFits`). A live SIM serial belongs to one number
  (`assertSimFree`, advisory lock on the serial).
- **Prices by layer:** `GET /v1/postpaid/packages` gives a layer its own column and the ones below; the rest is `null`.
- **Visibility:** `accounts()` loads all users and filters in memory; a GET request reads them once (`withRequestTree`), a write route reads afresh. `access/sign-in-cost.db.spec.ts` pins a signed-in GET's statements.
- **The tree and the wallet lock (DB.9, ADR 0023):** a sale reads the seller's path before its transaction and passes it in (`Sale.path`, `posPath`, `Completion.posPath` read by `TaskCompletion.pathOf` in `complete`, the settlement's T5 and a person's decision); under the lock `confirmedPath` reads only the path's rows and refuses with `409 DUPLICATE_REQUEST` when an account on it moved, was deleted or changed layer (a freeze, a stop or a price change does not refuse: the debit is the price quoted before, as before). `sales/sale-lock-tree.db.spec.ts` pins the statements under the lock and the races.
- **Seeding:** `CatalogSeed.onModuleInit` runs `ensureCatalog` and the layer roles on every start (idempotent).
- **Sessions:** the `sid` cookie is a random token (`auth/session-token.ts`); PostgreSQL keeps `Session.tokenHash`
  and Redis the key `session:<tokenHash>`. `Session.id` is the public handle (list, revoke, `operatorId`) and opens
  nothing. `saveSession` answers the token; `liveSession(token)` reads by its hash.
- **Secrets at rest:** `platform/secret-box.ts` (AES-256-GCM, a 12-byte nonce and the full 16-byte tag; `open` refuses any other size, so a tag cut short is never checked in part; `seal`, `open`, and `tryOpen`, which never throws and answers the

Indexes for the lists (plan 2026-11-17-database-scale, DB.1–DB.2): `(createdAt DESC, id DESC)` on `Line`,
`WalletEntry` and `Task` (NEWEST_FIRST); `Task(posId, createdAt DESC, id DESC)`; `WalletEntry(userId, createdAt DESC,
id DESC)`; `Task(lineId)`, `WalletEntry(actorId)`, `Session(userId)`, `TaskNote(authorId)`. For the daily purges (DB.13, migration `20261117190000_retention_indexes`): `Notice(createdAt)`, `LineCountSnapshot(day)`. Indexes Prisma cannot
state are raw SQL in their migration, not in the schema, and invisible to `prisma migrate diff`; the upgrade
rehearsal checks they exist: the partial uniques `Task_open_activation_iccid` / `_msisdn`, the partial
`WalletEntry_sale_or_refund_createdAt_id` (its predicate is `SALE_KINDS` with `amount < 0` or `REFUND_KINDS` with
`amount > 0`: rebuild it if those lists change), the partial `ProviderOperation_unsettled_id` (`unsettledPage`), the partial `WalletEntry_provider_createdAt_id` on `(providerId, createdAt DESC, id DESC) INCLUDE (providerCost) WHERE providerId IS NOT NULL` (migration `20261117220000_provider_ledger_index`, ADR 0025 P.3: the provider books' sums and ledger page), the partial `WalletEntry_provider_loss` on `(providerId, createdAt DESC, id DESC) WHERE providerLoss IS NOT NULL` (migration `20261117240000_provider_loss`: the summaries' count and the filter), the partial `WalletEntry_loss_createdAt` on `(createdAt DESC) WHERE providerLoss IS NOT NULL` (migration `20261118000000_provider_loss_created_at`, spec DB.5 P.8: the branch's losses over a period in its profit figures, proven by `EXPLAIN` in `branch-losses.db.spec.ts`), the unique partial `WalletEntry_charges_entry` on `(chargesEntryId) WHERE chargesEntryId IS NOT NULL` (migration `20261118100000_provider_loss_charged_later`, spec DB.5 P.9: one charge per given-back operation) and
the expression index `Notice_kind_taskId` on `(kind, payload->>'taskId')`, which `taskNoteSent` (raw SQL) filters.
`after()` writes the cursor as `column <= X AND (column < X OR id < Y)` so those indexes get a bound.
Search (DB.6, migration `20261117170000_search_trigram`): the extension `pg_trgm` and trigram GIN indexes on
`Line.msisdn`, `Line.iccid`, `Task.msisdn`, `WalletEntry.msisdn` (in the schema, `type: Gin`), which serve every
`contains` on a number; the upgrade rehearsal checks the extension and them. The request log's raw-SQL indexes and
its storage setting (DB.14) are checked there too.

## Known gaps (not done yet)

- A production api on this code does not start without its production settings (`production-config.ts`, ADR 0016);
  what each environment must set is in `docs/handover/technical-operations-ar.md`, section 6. After setting
  `SECRETS_KEY`, run `npm run seal-secrets --workspace api` once. A lost key locks app-2FA users out (the owner can
  clear 2FA per account).
- A renewal task stores no `unitPrice` (found in slice S.4 of the activation-settlement plan, left for the owner's
  separate review). A plain activation stores its `providerCost` since ADR 0025 P.1.
- A cut catalog list answers `capped: true` (`LIST_CAP`, 1,000) but no screen says so yet.
- `provider-operations` filters its match state in memory and `openDifferences` is a Node pass over a provider's
  priced operations (the match is simulated, not stored; a real reconciliation is an open item). An operation done at the provider but given
  back to the customer is in no provider's books (ADR 0025 P.7).
- An activation records its provider operation in its own transaction (`sales/lines.service.ts` `recordIn`) and the
  worker's dispatcher sends it once dispatch is approved for the provider (ADR 0017, 0018, 0019;
  `sales/activation-dispatch.db.spec.ts`). Still missing: a provider status check, a screen for `unknown`
  operations (plan `2026-11-10-provider-dispatcher.md`, "Not started"). Published outbox messages are pruned since DB.13
  (ADR 0024); those of an operation that is never applied (one without a task, or an exception left open) are kept.
- The activation settlement (ADR 0019, spec and plan `2026-11-10-activation-settlement.md`) is built up to S.12a:
  the schema, the reservation of a serial and a number, `capture`, sealed eSIM codes, the guards of the manual path,
  the request key, the dispatch gate and its review conditions (S.12b.0). Open: S.5's box, and S.12b, the first
  adapter, blocked until the owner supplies the provider's details (S.12b.1).
- Real provider adapters and the SMS/email gateways do not exist: `SimulatedProviderGateway` and `LogSender`.
  In production every line operation is therefore a branch task. The catalog adapter and the provider charges
  (`match-simulator.ts`) are still simulated everywhere.
