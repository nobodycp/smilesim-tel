## Rules

`.cursor/rules/backend-engineering.mdc` is the law for this app; `src/architecture.spec.ts` and `src/architecture-boundaries.spec.ts`
enforce it on every test run (a ratchet: a rule's violation count may only go down). What no refactor may change
about money is `docs/architecture/financial-invariants.md`. Read it before the first change.

## How a request runs

1. Middleware, on every route: `OriginMiddleware` (a write from another site is 403) → `RateLimitMiddleware` →
   `DoorMiddleware`.
2. Global providers (`modules/shared/api-providers.ts`, registered in `AppModule` and in every HTTP spec app):
   `ApiExceptionFilter` (every error is `{ message, code }`) and `EmptyBodyPipe` (a missing body is `{}`).
3. Office controllers: `ActivityInterceptor` then `ActorInterceptor`; the handler gets `@Actor()`.
4. The service: permission through `office/policy.ts` → `parseInput(<Schema>, body)` from `<domain>.schemas.ts` →
   rules (`office/rules/`, pure) → `<domain>.repository.ts` (one named method per query; a method that may run in
   a transaction takes the client). Money and status changes run in `UnitOfWork.runTx` on locked rows.
5. A line operation asks `ProviderGateway` whether the provider ran it; a refusal or a manual mode opens a task.

## Stack

NestJS 12 · Prisma 7 (`@prisma/adapter-pg`, PostgreSQL) · BullMQ + ioredis · argon2 · otplib (TOTP) · Swagger at `/docs` (non-production only) · Jest 30 + ts-jest 29 + supertest.

## Cross-cutting patterns

- **Permissions:** `ActorInterceptor` resolves the actor before the handler (declared after `ActivityInterceptor`, so
  refused sessions are still logged; pipes run after it, so 401 precedes 400). Services ask `office/policy.ts`
  (`requireGrant(actor, 'edit')`, `holds`, `requireOwner`, `refuseEntered`); none reads `actor.grants` itself.
  `testing/permissions.http.spec.ts` pins who gets past every route. An entered session cannot use `/auth` writes
  and only an account below the branch can be entered.
- **Errors:** `fail(status, code)` throws `ApiFailure`; `ApiExceptionFilter` answers `{ message, code }` for it,
  for framework errors, for a lost unique race (409) and a missing row (404); anything else is 500 `SERVER_ERROR`,
  logged. Status table: 400 invalid or refused by a rule · 401 no session · 403 not allowed · 404 missing or not
  visible · 409 conflict (`*_TAKEN`, `*_EXISTS`, `DUPLICATE_REQUEST`) · 429 rate limit.
- **Validation:** every body is parsed by a zod schema in `<domain>/<domain>.schemas.ts` through `parseInput()`
  right after the permission check (ADR 0002, finished 2026-11-10). Specific error codes keep their own checks.
  Query filters are still read with `text()`.
- **Activity log:** `@Activity(action, subjectKind, subject)` or `@NoActivity(why)` on every office write. The auth
  owner routes record through `ActivityRecorder` in the controller. `ActivityRecorder` is the platform's port
  (`shared/activity.ts`); auditing implements it (slice R.2).
- **Persistence:** `PrismaService` is injected; `runTx` = `$transaction` at Read Committed, notices published after
  commit.
- **Money:** Int agorot. `move()` locks the wallet row before reading it (ADR 0004); two wallets are locked in
  sorted order (`lockWallets`); a line is locked before any wallet. A task holds its price while open and charges
  the price it was opened at: completion **captures** the hold (`WalletLedger.capture`, ADR 0019 D10: the hold
  becomes the charge with no second ceiling check, refused when the wallet holds less than the task's hold);
  `move` and `capture` post through the same code. Two operations are the exception to the fixed price, by
  the owner's rule (rule 1.5): a package switch's difference and a disconnect's refund are the money of the day
  the operation is carried out, worked out in the completion's transaction. A switch's amount is covered by its
  hold up to the hold's size and only an increase beyond it is checked against the ceiling; a disconnect's refund
  is a credit and its task holds nothing (`lines/execution-date-settlement.db.spec.ts`). Proof: `wallets/wallet-concurrency.db.spec.ts`, `lines/line-concurrency.db.spec.ts`
  (PostgreSQL, CI `db` job). `lines/activation-reservation.db.spec.ts` shows the reservations under concurrency.
- **Lock order (ADR 0019):** task row → line row → the keys of a serial and a number (`lockClaim`: serial, then
  number) → provider operation → wallets in sorted order. A transaction takes only what it needs, in that order.
- **Line state:** a status changes only through `moveLineStatus` (guarded) on a line locked with `lockLine`; a
  request validated before the transaction calls `lockUnchanged` first (409 when another operation got there
  first); a task whose line moved on is refused (`assertTaskFits`). A live SIM serial belongs to one number
  (`assertSimFree`, advisory lock on the serial).
- **Prices by layer:** `GET /office/packages` gives a layer its own column and the ones below; the rest is `null`.
- **Visibility:** `accounts()` loads all users and filters in memory.
- **Seeding:** `CatalogSeed.onModuleInit` runs `ensureCatalog` and the layer roles on every start (idempotent).
- **Sessions:** the `sid` cookie is a random token (`auth/session-token.ts`); PostgreSQL keeps `Session.tokenHash`
  and Redis the key `session:<tokenHash>`. `Session.id` is the public handle (list, revoke, `operatorId`) and opens
  nothing. `saveSession` answers the token; `liveSession(token)` reads by its hash.
- **Secrets at rest:** `shared/secret-box.ts` (AES-256-GCM, a 12-byte nonce and the full 16-byte tag; `open` refuses any other size, so a tag cut short is never checked in part; `seal`, `open`, and `tryOpen`, which never throws and answers the
  value or why it cannot be read; AES-256-GCM, `v1:` prefix). `PrismaAuthStore` seals
  `twoFactorSecret` / `pendingTwoFactorSecret` on write and opens them on read; a value stored before sealing reads
  as it is. `src/seal-secrets.ts` (`npm run seal-secrets --workspace api [-- --dry-run]`) seals what is already stored: authenticator secrets, and the eSIM codes of lines and tasks through `src/seal-esim-codes.ts` (batches by primary key, guarded writes, restartable, counts only). **Two-step methods that can be carried out** (spec 2026-11-12-two-factor-available-methods): `auth/message-sender.ts` `MessageSender.delivers(channel)` (`LogSender` delivers nothing); `auth/two-factor-policy.ts` `availableMethods` (the app, plus SMS / email while the sender delivers) and `enrolmentChoices`; a layer or account set to an unavailable method is refused with `METHOD_UNAVAILABLE` before anything is written or anyone is signed out; stored settings are kept and their accounts enrol with an available method. `src/two-factor-methods.ts` (`npm run two-factor-methods --workspace api`) is the read-only report of stored SMS / email settings, accounts by id only. `src/reservation-conflicts.ts` (`npm run reservation-conflicts --workspace api`) is the read-only report to run before deploying the reservation indexes; it names tasks by id, shows a serial or a number by its last four characters (`reservation.rules.ts` `maskedTail`) and a failure by `errorCode`.
- **Config and logs:** `config.ts` only; Nest `Logger` only (`shared/log.ts`).
