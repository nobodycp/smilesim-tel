# إعادة هيكلة Pearl — المرحلة ٣: صفحات التفاصيل

هذا السبك يغطي **الشريحة الثالثة** من إعادة هيكلة الواجهة الموصوفة بـ`docs/superpowers/specs/2026-11-01-pearl-rebuild-phase1-shell-home-design.md`. القرارات العامة (الهوية، الطبقة التقنية، الخطوط) مُتّخذة هناك وسارية هون بدون تكرار.

## لماذا

على عكس المرحلتين ١ و٢، فحص الصفحات الست المخطّطة لهذه المرحلة (`/companies/[code]`, `/companies/[code]/[provider]`, `/providers/[code]`, `/numbers/[id]`, `/providers/[code]/[packageCode]`, `/users/[login]`) أظهر إنها **مبنية بانضباط أعلى بكثير** من صفحات الجداول قبل المرحلة ٢ — أغلبها يستخدم `.pane`/`DataTable`/`.steps`/`RowMenu`/`badge`/`label.check`/`Money`/`bdi dir="ltr"` بشكل صحيح ومطابق لـ`content-ui.mdc` من دون لمس. هذا يعني نطاق العمل الفعلي هون أخفّ بكثير من المرحلتين السابقتين — ومُتعمَّد إننا ما نخترع مشاكل غير موجودة لمجرد التماثل مع حجم المراحل الأخرى.

المشكلتان الحقيقيتان اللتان وُجدتا:

1. **نمطا "حقائق" متنافسان بنفس الكود، بنفس عيب المرحلتين ١ و٢:**
   - `.facts` (صفحة الرقم `numbers/[id]`): `<dl>` بعمود واحد، كل حقيقة بسطر عريض لحاله. فيها عيبان فعليان: (أ) `.facts > div { border-bottom: ... }` خاصية فيزيائية صريحة بدل `border-block-end` — مخالفة مباشرة لـ`direction-theme.mdc`. (ب) تخطيط عمود واحد يُهدر عرض الشاشة الكبيرة (مخالفة `screen-size.mdc`: "وقف عرض الشاشة ... عمود واحد يفضل فاضي خطأ").
   - `.account-facts` (صفحة حساب المستخدم `users/[login]`): شبكة بخمسة أعمدة، نفس الغرض بالضبط (عرض حقل/قيمة)، لكن تعريف CSS منفصل تمامًا وبنية `div`/`span`/`b` بدل `dl`/`dt`/`dd`.
2. **صفحة حساب المستخدم (`users/[login]/page.tsx`) غير موجودة بتاريخ git إطلاقًا** (`??` بـ`git status`) — شغل صاحب المشروع الجاري على ميزة الصلاحيات/الأدوار، لم يُلتزم بعد. بما إننا نقلنا كل العمل للفرع `main` مباشرة (قرار المستخدم)، هاي أول فرصة تدخل فيها الصفحة لتاريخ Git إطلاقًا.

**تصحيح مهم أثناء الاستكشاف:** شُبهة أولية بوجود `div` مكرر (`.grant-line.head`) بنفس صفحة حساب المستخدم تبيّنت أنها **خطأ تحليل، مش خطأ كود**. فحص `desk.css` أظهر أن `.grant-head`/`.grant-board` شبكة متعمَّدة بعمودين (لعرض قائمة الصلاحيات بعمودين جنب بعض على الشاشة العريضة)، والعنصران هما رأسا العمودين، وفيه قاعدة `@media` تُخفي الرأس الثاني على الشاشة الضيقة. هذا تصميم صحيح ولن يُمس.

## القرارات

1. **سبك وخطة واحدة تغطي السبع صفحات** (الست المخطّطة بخارطة المرحلة ١ + صفحة حساب المستخدم المكتشفة كنفس الفئة). نفس منهج المرحلتين السابقتين: نمط مشترك أولاً (Facts الموحّد)، ثم مراجعة/تطبيق صفحة بصفحة.
2. **توحيد نمط الحقائق**: `.facts` يتحول لشبكة متجاوبة (أعمدة تتكيف مع العرض المتاح، تنهار لعمود واحد على الموبايل — بنفس روح `.account-facts` الحالية)، مع تصحيح `border-bottom` إلى `border-block-end`. البنية الدلالية تبقى `<dl>`/`dt`/`dd` (أصح من `div`/`span`/`b` من ناحية HTML دلالي). يُطبَّق على `numbers/[id]` (موجود فيها فعلًا) و`users/[login]` (تستبدل `.account-facts` بنفس نمط `.facts` الجديد). بعد التطبيق، `.account-facts` وكل قواعدها الفرعية تُحذف نهائيًا من `desk.css`.
3. **صفحة حساب المستخدم تُلتزم بالكامل بهذه المرحلة** (منطق + أنماط سوا) — لا داعي لتقنية "إعادة بناء النسخة الملتزمة" (`git show HEAD:<file>` + `hash-object`) المستخدمة بالمراحل السابقة للفصل عن عمل صاحب المشروع غير المُلتزم، لأنه **لا يوجد أي أصل ملتزم إطلاقًا لهذا الملف** — كل محتواه الحالي هو "عمل صاحب المشروع الجاري" بحد ذاته، وسيصير هو نفسه محتوى أول commit له.
4. **الديف المكرر `.grant-line.head` ليس خطأ ولن يُمس** — تصميم شبكة بعمودين مقصود (أنظر "لماذا" أعلاه).
5. **مربع الاختيار بقسم "الأدوار الإضافية" (`label.grant-line` بدل `label.check`) ليس مخالفة ولن يُمس** — الحجم مضبوط فعليًا (`18×18px` عبر `.grant-line > input[type='checkbox']`) لمحاذاة عمود التحكم مع بقية صفوف الصلاحيات أعلاه؛ تحويله لـ`label.check` يكسر محاذاة الأعمدة مع باقي `.grant-board`.
6. **الفورمز الداخلية ضمن تابات صفحات التفاصيل** (لوحة الأسعار، تجديد السعر، تحويل الخط، تحديث الرقم، تبديل الشريحة، إضافة عرض سعر بصفحة الباقة) **داخل نطاق هذه المرحلة** — هي جزء بنيوي من الصفحة نفسها معروضة ضمن `.pane-body`/`.command-forms`/`.account-fund`، وليست ديالوجات منبثقة منفصلة؛ مرحلة ٤ (حسب خارطة المرحلة ١) تبقى مخصصة للديالوجات الفعلية (`Dialog` من `components/dialog.tsx`: فتح حساب، تمويل، سقف، تفعيل خط).
7. **لا تغيير بمنطق الباك إند أو `lib/api.ts`** — عمل بصري/تركيبي بحت.
8. نفس قرارات المرحلة ١ بالهوية البصرية، الطبقة التقنية، والخطوط سارية بلا تغيير.

## نطاق هذه المرحلة

### داخل النطاق

**نمط Facts الموحّد (`desk.css`):**
- استبدال تعريف `.facts` الحالي (عمود واحد + `border-bottom`) بشبكة متجاوبة بحدود منطقية (`border-block-end`).
- حذف `.account-facts` وكل قواعدها الفرعية بعد تحويل مستخدمها الوحيد.

**`companies/[code]`, `companies/[code]/[provider]`, `providers/[code]`:** مراجعة بصرية فقط (جدول/شارات/أزرار/حالة فاضية) — لا تغيير متوقَّع لأنها نظيفة أصلًا؛ تُثبَت بلقطات شاشة بدل افتراض سلامتها بلا دليل.

**`numbers/[id]` (كرت الرقم):** تحويل `.facts` لنمط الشبكة الجديد. مراجعة بصرية للتابات الثلاثة (عمليات/تفاصيل/سجل)، الشارات، والفورمز داخل `.command-forms`.

**`providers/[code]/[packageCode]` (ورقة الباقة) — الأعقد:** مراجعة بصرية شاملة لكل التابات السبعة (نظرة عامة/تشغيل/أسعار/تجديدات/تحويلات/أرقام/عروض)، لوحة الأسعار (`.price-board`/`.account-fund`)، مفتاح التفعيل (`.live-switch`)، جدول العروض (`RowMenu`)، جدول الأرقام بتحديد متعدد. لا تغيير بنيوي متوقَّع — الصفحة متوافقة أصلًا مع الأنماط الموثّقة.

**`users/[login]` (صفحة حساب المستخدم) — أول التزام لها بالكامل:**
- استبدال `.account-facts` بنمط Facts الموحّد.
- التزام كامل محتوى الصفحة (منطق الصلاحيات/الأدوار + الأنماط) لأول مرة بتاريخ Git.
- مراجعة بصرية للوحة الصلاحيات (`.grant-board`)، قسم الأدوار الإضافية، وزر الحفظ.

### خارج النطاق

- أي ديالوج منبثق منفصل (`Dialog`) — مرحلة ٤.
- تغيير تخطيط الصلاحيات ثنائي الأعمدة أو محاذاة مربع اختيار الأدوار الإضافية — ليسا خللين (قرار ٤، ٥).
- أي تغيير بـ`lib/api.ts` أو العقود مع الباك إند.
- الطبقة التقنية والخطوط — نفس قرارات المرحلة ١.

## التحقق

- لقطات 1280px وmobile (390px) للصفحات السبع، فاتح/غامق، عربي كحد أدنى + عيّنة إنجليزي/عبري لصفحة أو صفحتين تمثيليتين (نفس منهج المرحلة ٢)، خصوصًا تأكيد أن نمط Facts الموحّد يتكيّف صح بعرض 1280 (عدة أعمدة) وينهار صح بعرض 390 (عمود واحد) بكلا الصفحتين (`numbers/[id]`, `users/[login]`).
- `npx tsc --noEmit` و`next build` بدون أخطاء.
- `npx playwright test` خضراء (مع تجاهل أي فشل موجود مسبقًا وموثّق كغير مرتبط، بنفس تحفظ المرحلتين ١ و٢).
- تحديث `DESIGN.md` بتوثيق نمط Facts الموحّد كمكوّن/نمط رسمي إذا لم يكن موثّقًا بدقة كافية حاليًا.
- بعد الالتزام الأول لصفحة `users/[login]`، تحديث `.superpowers/sdd/progress.md` بملاحظة أن هذا الالتزام يحمل منطق عمل صاحب المشروع كاملًا لأول مرة (لا فصل ممكن، كما هو موضّح بالقرار ٣).

## النتيجة

**قبل:** المهمتان ١ و٢ حوّلتا `.facts` و`.account-facts` لنمط شبكة موحّد، لكن بالتحقق البصري الفعلي (لا بافتراض) — خصوصًا صفحة كرت الرقم `numbers/[id]` التي لم يتسنَّ لمهمة ١ فحصها بصفحة حقيقية (لا يوجد سطر `Line` مزروع بقاعدة بيانات التطوير، ومحاولة تفعيل رقم جديد بالواجهة فشلت بخطأ سقف رصيد غير مرتبط) — بقي هذا التحقق معلّقًا. بالتوازي، فحص بصري حقيقي (لا افتراضي) للصفحات الخمس الأخرى (`companies/[code]`, `companies/[code]/[provider]`, `providers/[code]`, `providers/[code]/[packageCode]`) كشف خللين حقيقيين لم يكونا معروفين سابقًا، كلاهما بصفحة ورقة الباقة `providers/[code]/[packageCode]`:
1. **تاب "الأرقام" بورقة الباقة كان يعمل صح** (يعرض رسالة "لا أرقام بعد." عند فراغ القائمة)، **لكن تاب "المخصصون" (العروض الخاصة) لم يكن كذلك** — جدول فارغ تمامًا (رأس بلا صفوف، بلا أي رسالة) لأي باقة بلا تسعير مخصص لحساب معيّن (الحالة الشائعة لأغلب الباقات)، لأن استدعاء `DataTable` هناك لم يُمرَّر له `empty` إطلاقًا، خلافًا لتاب "الأرقام" بنفس الملف.
2. **السبب الجذري لعدم ظهور رسالة "لا أرقام بعد." كان كامنًا أصلًا بمكوّن `DataTable` المشترك نفسه** (`components/data-table.tsx`) وليس بصفحة ورقة الباقة: الفرع `bare` كان يُرجع الجدول فورًا (`if (bare) return table;`) **قبل** الوصول لمنطق `keepHead`/`empty`، فيُفقَد تمامًا أي استدعاء يجمع `bare` مع `keepHead` و`empty` معًا — وهذا بالضبط ما فعلته صفحة ورقة الباقة بتاب "الأرقام"، فكانت النتيجة الفعلية المعروضة هي رأس جدول فاضٍ بلا أي رسالة، رغم أن الكود كان "يبدو" صحيحًا باستدعائه الثلاثي `bare`+`keepHead`+`empty`.

**بعد:**
- **إصلاح `components/data-table.tsx`:** الفرع `bare` أصبح يتحقق من حالة `hollow` (فراغ + وجود `empty`) قبل الإرجاع — إن كانت الحالة فاضية يُرجع الجدول متبوعًا بـ`EmptyState` سوا (حالة `bare`+`keepHead`+`empty` التي كانت مكسورة)، وإلا يُرجع الجدول وحده كالسابق (الاستخدامان الآخران لـ`bare` بنفس الصفحة — تاب "التشغيل" بلا `empty` إطلاقًا، وتاب "المخصصون" بعد إصلاحه بـ`empty` بلا `keepHead` — بقيا بلا أي تغيير بالسلوك، تم التحقق). تاب "الأرقام" بورقة الباقة يعرض الآن فعليًا "No numbers yet." (الإنجليزية) / "لا أرقام بعد." (العربية) تحت رأس الجدول، بدل جدول فاضٍ صامت.
- **إصلاح تاب "المخصصون":** أُضيف مفتاح ترجمة جديد `noOffers` بالعربية/الإنجليزية/العبرية ("لا تخصيصات بعد." / "No special prices yet." / "אין מחירים מיוחדים עדיין.")، ومُرِّر كـ`empty` لاستدعاء `DataTable` هناك. يعرض التاب الآن `EmptyState` فعلي (أيقونة + نص) بدل جدول فاضٍ بلا أي مؤشر.
- **صفحات `companies/[code]`, `companies/[code]/[provider]`, `providers/[code]`:** فحص بصري كامل ببيانات حقيقية (شركة سلكوم/cellcom ومزوّدها الوها/alloha) — لا خلل. الجداول، الشارات، وزر الرجوع تعمل صح بكل التركيبات المفحوصة.
- **صفحة ورقة الباقة `providers/[code]/[packageCode]`:** بقية التابات السبعة (نظرة عامة، إجراءات الحزمة، الأسعار، التجديد، التبديل) ببيانات حقيقية (باقة "الوها · 400 جيجا") سليمة بصريًا — لا خلل إضافي غير الاثنين أعلاه.
- **`numbers/[id]` و`users/[login]` — تحقق نمط Facts الموحّد (الخطوة ٤):** عند 1280px تعرض `.facts` 5 حقائق بصف واحد (`users/[login]`) و8 حقائق بصفين (5+3، `numbers/[id]`) — تعدد أعمدة فعلي بدون أي صف منفرد الشكل فاضي المظهر. عند 390px تنهار الشبكة لعمودين (لا عمود واحد كما افترضت الخطة، لكنه سلوك `auto-fit`/`minmax(9rem,1fr)` الصحيح ومطابق لما وثّقته المهمة ٢ سابقًا) بلا أي تمرير أفقي. الحد السفلي لكل حقيقة يستخدم `border-block-end` فيتبدّل جهته صح بين عربي (RTL) وإنجليزي (LTR) — تم تأكيده بصريًا بكلا الاتجاهين، إضافة لعيّنة عبرية (RTL أيضًا) على الصفحتين. الثيم الغامق يستخدم ألوان `--rd-*` صح على الصفحتين (لا ألوان ثابتة فاتحة).

**لقطات الشاشة:** 116 لقطة بـ`docs/visual-review/2026-11-02/phase3-detail-pages/`: 3 صفحات بسيطة (`companies/[code]`, `companies/[code]/[provider]`, `providers/[code]`) × (فاتح/غامق) × (عربي/إنجليزي) × (1280px/390px) = 24 لقطة، + صفحة ورقة الباقة بسبعة تابات × (فاتح/غامق) × (عربي/إنجليزي) × (1280px/390px) = 56 لقطة، + `users/[login]` بـ(فاتح/غامق)×(عربي/إنجليزي)×(1280/390) = 8 + عيّنة عبرية (1280/390) = 2، + `numbers/[id]` بثلاثة تابات × (فاتح/غامق) × (عربي/إنجليزي) × (1280/390) = 24 + عيّنة عبرية لتاب التفاصيل (1280/390) = 2. كل اللقطات بأسماء وصفية بنفس مجلد التاريخ `2026-11-02`.

**منهجية اللقطات:** الصفحات الخمس ببيانات حقيقية (تسجيل دخول فعلي بحساب `branch`/كلمة السر التجريبية، شركة سلكوم ومزوّدها الوها اللذان لديهما بيانات مزروعة فعلية). صفحة `numbers/[id]` وحدها احتاجت اعتراض Playwright مباشر لمسار `GET /api/office/lines/<id>` بسطر `Line` وهمي واقعي (نفس قيود المهمة ١: لا يوجد سطر خط مزروع بقاعدة بيانات التطوير)، مع إبقاء بقية مسارات الجلسة (`/me`, الصلاحيات) حقيقية — سكربت مؤقت (`apps/web/tests/zz-phase3-shots.mjs`) حُذف بعد الانتهاء، بنفس انضباط المرحلة ٢.

**التحقق المنفَّذ:** `npx tsc --noEmit` نظيف (قبل وبعد كلا الإصلاحين)، `next build` نجح بدون أخطاء (مع التراجع عن تعديل `tsconfig.json` التلقائي مرتين). `npx playwright test`: 37 ناجح من 40 (قبل وبعد الإصلاحين، نفس العدد بالضبط)؛ الثلاثة الفاشلة مطابقة تمامًا لقائمة المرحلتين ١-٢ (`companies-shelf.spec.ts` فحصه الفعلي لنص "عدد الأرقام:" يتعطّل بسبب إعادة هيكلة غير مُلتزمة لصاحب المشروع لتاب "نظرة عامة" بنفس الملف — مؤكَّد عبر `git diff`؛ `login.spec.ts` إنهاء الجلسة و`tools-pages.spec.ts` نقر مزدوج يلمسان ملفات فيها تعديلات غير مُلتزمة سابقة لصاحب المشروع كذلك) — لا فشل جديد ناتج عن أي من الإصلاحين.

**انضباط Git:** كل من `apps/web/lib/copy/{ar,en,he}.ts` و`apps/web/app/providers/[code]/[packageCode]/page.tsx` كانت فيها تعديلات غير مُلتزمة سابقة لصاحب المشروع (إعادة هيكلة تاب "نظرة عامة"، مفاتيح ترجمة جديدة لميزات أخرى قيد العمل). إصلاح تاب "المخصصون" التُزم عبر إعادة بناء النسخة الملتزمة (`git show HEAD:<file>` + تطبيق السطر الواحد المطلوب فقط + `hash-object`/`update-index`)، تمامًا بنفس أسلوب المراحل السابقة، تاركًا تعديلات صاحب المشروع الأخرى غير ملتزمة بشجرة العمل كما هي. إصلاح `components/data-table.tsx` التُزم مباشرة (الملف كان نظيفًا، مطابقًا تمامًا لـ`HEAD`، بلا أي عمل غير ملتزم لصاحب المشروع).

**محدودية معروفة بالتحقق:** صفحة `numbers/[id]` اعتُبرت ببيانات وهمية واحدة فقط (سطر خط نشط، تاريخ تفعيل/تجديد/تحديث رقم) — لا تغطي كل تركيبات الحالة (مجمّد/مفصول) أو كل التابات بكل تفاصيلها الحدّية؛ كافٍ للتحقق من تخطيط `.facts` والصفحة عمومًا، لكنه ليس بديلاً عن اختبار بسطر حقيقي من قاعدة البيانات متى توفّر.
